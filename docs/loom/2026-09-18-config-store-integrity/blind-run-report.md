# 設定檔存 profile 不再遺失、不再截斷 — 我實際試了什麼、結果如何

**結論：七條驗收條件全部通過（PASS）。** 其中第 3 條（刪除順序）在「刪密碼」這一半
本來就是對的，這次真正補上的是「鑰匙圈拒絕刪除時，程式要老實講失敗，而不是
裝作成功」；第 6 條（不相干的 profile 不受影響）改之前就大致成立，這次是把它
和其他修正一起釘成測試，不是新修好的行為。真正從「壞」修到「好」的是第 1、2、
4、5 條。單元測試 399 項全綠；需要連真實資料庫的兩批測試因為叢集連不上而
**無法驗證**，不算這次的失敗，但也不能算通過。

試用日期：2026-09-19。在專案的一份全新乾淨副本（版本 `3a7ba91`）上進行，
設定檔位置全程指向一個用完即丟的暫存資料夾，鑰匙圈全程換成假的、只存在

## 一句話：這個修改對你來說是什麼意思

你在這個工具裡存好幾組 Redshift 連線設定（不同叢集、不同帳號），這些設定
存在你電腦上的一個檔案裡。**改之前**，這個檔案每次寫入都是「整個讀出來、
改一筆、整個蓋回去」，中間完全沒有防護，於是：如果你同時開好幾個視窗設定
好幾組連線，會憑空少掉好幾組（我這次測到八個一起設定，改之前平均只留一到
三組，改之後八個全部都在）；如果寫到一半當機或磁碟滿了，整個檔案可能被
截斷成一堆半吊子文字，連同其他不相干的設定一起壞掉；刪除一組設定時，
如果你的系統鑰匙圈剛好鎖住，密碼可能留在鑰匙圈裡卻沒有任何畫面看得到它、
刪得掉它。**改之後**，這三個坑都補上了：多組同時寫入會排隊、不會互相蓋掉；
寫到一半失敗，檔案會維持改之前的樣子，一個字元都不會少；刪除時鑰匙圈失敗
會清楚地告訴你「刪除失敗，去解鎖鑰匙圈再試一次」，而不是悄悄裝作已經刪掉。

## 你要求的七件事，一條一條試

### 1. 八個同時發生的寫入，八組不同的設定，最後八組都要在

- **我怎麼試的**：不是用程式裡的「執行緒」互相搶時間那種模擬,而是真的開
  **八個獨立的作業系統行程**，各自呼叫一次「寫入設定」，八個名字各不相同，
  全部指向同一個暫存設定資料夾。等八個都跑完，把整個設定檔讀出來數一數。
  這整套流程我跑了三次。

- **結果**：三次，每次八個行程結束代碼都是 0（沒有任何一個出錯），每次
  讀出來的設定名單都是完整的八組，一組都沒少。

- **證據**：三次執行的完整輸出，逐次列出「目前有的設定名單」與「是否
  八組齊全」，三次皆為是。

- **判定：PASS（通過）**

---

### 2. 寫到一半失敗，事後看不出任何「寫一半」的痕跡，連正在讀檔的人也看不到

- **我怎麼試的**：我先寫好兩組設定當「已經在用」的基準狀態，把檔案的原始
  位元組記下來。接著讓負責把設定轉成檔案格式的那一步在執行到一半時直接
  丟例外（模擬硬碟出問題、序列化失敗這類真實會發生的狀況）。丟例外的同時，
  我另外開一條背景執行緒，以極短間隔反覆去「打開檔案、當場解析」，看它有
  沒有機會撞見一份寫一半、解析不出來的檔案。

- **結果**：寫入呼叫如預期地把例外往外丟；事後把檔案位元組跟基準一字不差
  比對，**完全相同**；背景那條一直在偷看的執行緒，**沒有任何一次**撞見解析
  失敗；失敗過後檔案仍然能正常解析出原本那兩組設定。

- **證據**：呼叫前後的完整位元組字串（相同）、背景偷看執行緒的失敗紀錄
  （空，代表零次失敗）、失敗後重新解析出的設定名單（`alpha`、`beta`，
  跟基準一致）。

- **判定：PASS（通過）**

### 3. 刪除一組設定時，要先刪鑰匙圈裡的密碼再刪欄位；鑰匙圈刪不掉時要老實回報失敗

- **我怎麼試的**：先建一組設定並在假鑰匙圈裡放一筆對應密碼，然後把假鑰匙圈
  的「刪除」動作改成永遠丟出「鑰匙圈被鎖住」這個系統會實際丟出的例外，
  再呼叫刪除。之後把假鑰匙圈改回正常運作，重新呼叫一次刪除，看兩個地方
  （設定欄位、鑰匙圈密碼）是不是真的都乾淨了。

- **結果**：鑰匙圈鎖住時，刪除呼叫**丟出了一個專門的錯誤型別**（不是回傳
  一個含糊的「假／失敗」），設定欄位在這個當下**完全沒被動過**，你之後解鎖
  鑰匙圈再刪一次還是刪得到同一組完整的設定。等鑰匙圈恢復正常後重試，
  這次密碼和欄位**兩邊都乾淨地消失了**。

- **證據**：例外的型別名稱（就是需求書指定要用的那個專屬型別，不是普通的
  `False`）、失敗當下讀出的欄位內容（仍然完整）、恢復正常後刪除的回傳值
  與兩邊的最終狀態（都已清空）。

- **誠實說明**：「先刪密碼」這個順序本身，是這次修改**新加上去**的；但
  「鑰匙圈失敗時欄位不受影響」這件事，以及專屬錯誤型別的存在，都是這次
  一起做的。如果只看「刪除最終能不能成功」，改之前也能刪成功——這次真正
  補上的是「失敗時讓你知道失敗了，而不是悄悄留一顆孤兒密碼在鑰匙圈裡」。

- **判定：PASS（通過）**

### 4. 刪掉的設定如果正是目前「使用中」指標指向的那組，指標要跟著清掉

- **我怎麼試的**：先建兩組設定 X、Y。情境一：把「使用中」指標指向 X，
  刪除 X，看指標還剩什麼。情境二：把指標指向 Y，刪除 X（不是指標指的那組），
  看指標是不是仍然安然指著 Y。

- **結果**：情境一，刪除 X 之後指標**變成「沒有指向任何東西」**（不再誤指
  一個已經不存在的設定）。情境二，刪除 X 之後指標**仍然精準指著 Y**，完全
  沒被誤動。

- **證據**：兩個情境刪除前後讀出的指標值（情境一：`X` → 空；情境二：
  `Y` → `Y`，不變）。

- **判定：PASS（通過）**

### 5. 需求書隨附的併發測試，在改動前的舊程式上要是紅的，在這次的版本上要是綠的

- **我怎麼試的**：這條是最容易被「其實沒換到程式」這個陷阱騙過去的一條，
  上一次負責驗證這個專案的人就差點栽在這裡（複製整個資料夾時，裡面的
  虛擬環境仍然偷偷指回新版程式，讓「改回舊版」形同虛設）。所以我這次
  **沒有用複製資料夾**的方式，而是分別用 `git worktree` 從「分支起點」和
  「這次的版本」各自建立一份完全獨立的副本，各自重新安裝一次相依套件，
  **在跑任何數字之前先印出程式實際載入自哪個路徑**，確認兩份副本互不
  污染，才開始跑需求書指定的那支併發測試。

- **結果**：獨立確認過兩份副本各自載入自己該載入的程式碼之後——

  ```
  分支起點（改動前）：跑那支併發測試 → 失敗
    「8 組設定裡有 5 組被改動前的無鎖讀-改-寫弄丟了：
     profile1, profile2, profile5, profile6, profile7」

  這次的版本（改動後）：跑同一支測試 → 通過
  ```

- **證據**：兩次執行各自先印出的程式載入路徑（分別落在「分支起點副本」與
  「這次版本副本」各自的資料夾裡，不是同一個地方）、改動前的失敗訊息
  （逐字列出哪五組設定遺失）、改動後的通過紀錄。

- **判定：PASS（通過）**

### 6. 一次寫入或刪除，除了正在動的那一組之外，之前就存在的其他設定要一字不動地留著

- **我怎麼試的**：先建三組設定，把它們讀出來當基準。寫入第四組設定後，
  重新讀出前三組，跟基準逐字比對。接著刪除其中一組，再讀出剩下沒被刪的
  兩組加上剛才新寫的第四組，同樣逐字比對。

- **結果**：新增第四組之後，原本三組**逐字不變**；刪除其中一組之後，
  剩下的其他組**同樣逐字不變**，被刪的那組確實消失。

- **證據**：寫入前後三組基準的比對結果（相同）、刪除前後其餘組別的比對
  結果（相同）、被刪除的那組確認讀不到。

- **誠實說明**：這件事在改動前的舊程式，只要「沒有同時發生第二個寫入」，
  單獨一次寫入本來就大致不會動到別組——真正的風險是本篇第 1、2 條講的
  「同時多個寫入」或「寫到一半失敗」才會牽連到別組。這一條在單一、依序
  操作的情境下改之前就成立，這次是把它和前面幾條修正一起釘成測試，防止
  日後改壞，而不是這次才修好的新行為。

- **判定：PASS（通過）**

## 除了七條驗收條件之外，我還試著把資料弄丟

### 設定檔如果是一個連到別處的捷徑（symlink）呢？

需求書提到之前有一版曾經把這種捷徑「寫壞」——寫入時捷徑消失、變成一個
普通檔案，真正的目標檔案從此再也收不到新設定。我實測：把設定檔位置換成
一個指向暫存資料夾外某處的捷徑，寫入一組設定後，**捷徑本身還在、還是
指向原本的目標**，而且新設定**確實出現在捷徑指向的那個真正檔案裡**。
沒有被寫壞。

### 寫到一半被強制關閉（比磁碟故障更粗暴）呢？

我用真正的系統訊號，在寫入行程「已經開了暫存檔、還沒改名成正式檔案」的
那個瞬間直接強制終止它，重複三次。結果：

- **確實會留下垃圾**：三次強制關閉，設定資料夾裡確實累積了三個沒人清掉的
  暫存檔案（這是任何「先寫暫存檔再改名」的設計在被強制關閉時都躲不掉的
  物理限制）。
- **下一次正常寫入會自動清掉**：我把這些垃圾檔案的時間戳改成看起來已經放了
  一天，再讓程式做一次正常寫入，垃圾**確實被清乾淨**。
- **清理不會誤殺正在寫的人**：我模擬一個「正在寫入、還沒寫完」的行程，
  它自己留下的暫存檔案是全新的（不到一天），清理動作在同一時間跑，
  **完全沒有動到這個還活著的暫存檔**。
- **清理不會動到你自己的備份**：我在資料夾裡放了一個你可能自己建立的
  `config.toml.backup` 檔案，清理前後內容**一字不動**。

### 用奇怪的設定名稱去踩邊界呢？

我試了空字串、名字裡帶換行、名字是 `../something`、名字裡帶 NUL 位元組、
一個 4096 字元的超長名字。五種**全部寫入成功、讀得回來、沒有讓程式當掉**，
也**沒有任何一種讓寫入的位置跑到設定資料夾以外**——因為這個名字只是存進
設定檔內部的一個欄位名稱，從來不會被當成檔案路徑的一部分去組合，所以
`../something` 這種路徑穿越手法在這裡沒有機會發揮作用。這點我認為是
這個設計本來就穩妥的地方，不是這次修改新補的洞。

## 需要連真實資料庫的測試

不需要連資料庫的那一批（399 項）全部跑完、全部綠燈。需要連真實資料庫的
兩批測試，我在動手跑之前先直接對你叢集的位址、通訊埠做了一次最原始的
「能不能連上」測試（不透過這個專案的任何程式碼），結果是**連線逾時**——
在應用程式的邏輯有機會出手之前，網路本身就已經連不上了。所以：

| 這一批 | 這次的狀態 |
|---|---|
| 不需要資料庫的單元測試（399 項） | **全部跑完、全綠** |
| 需要真實叢集的整合測試 | **無法驗證**（連線逾時，發生在程式邏輯之前，不算這次的失敗） |
| 需要真實叢集的 MCP 協定測試 | **無法驗證**（同上） |

「無法驗證」不等於「通過」——等你的叢集連線恢復之後，這兩批還是得再跑
一次才算數。

## 對你既有的資料做了什麼

**什麼都沒動。** 整個驗證過程中，程式讀寫設定的位置全程指向一個用完即丟的
暫存資料夾，鑰匙圈也全程換成假的、只存在程式變數裡。驗證結束後我直接檢查
了你真正的設定檔：修改時間、檔案權限、內容都跟驗證開始前完全相同，而且
依然能正常解析——代表它從頭到尾沒有被這次驗證打開來寫過。

至於這個修改**上線之後**對你既有資料的影響：設定檔格式沒有改，既有設定
不需要轉換、不需要備份，成功寫入的內容和以前一模一樣。改變的只有「多個
同時發生的寫入不會再互相蓋掉」「寫到一半失敗不會再留下半吊子檔案」「刪除
失敗會老實告訴你，而不是裝沒事」。你目前唯一的一組設定（`default`）沒有
被這次驗證碰過。

## 我不確定你要不要

1. **需要真實叢集的那兩批測試，要不要等你的連線恢復之後再請人補跑一次？**
   這不是這次修改造成的問題，但在你真正核准這次改動之前，這兩批終究是
   沒被驗證過的。
2. **暫存垃圾檔案清理的「多久算垃圾」門檻（目前設定為一天），你覺得合理嗎？**

   清掉，超過一天的才會被清掉。如果你的使用情境裡機器常常一放好幾天不重開，
   這個門檻可能值得你知道它的存在。
