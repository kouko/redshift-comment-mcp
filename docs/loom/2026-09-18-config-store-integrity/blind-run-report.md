## 一句話：這個修改對你來說是什麼意思

你在這個工具裡存好幾組 Redshift 連線設定（不同叢集、不同帳號），這些設定
存在你電腦上的一個檔案裡。**改之前**，這個檔案每次寫入都是「整個讀出來、
改一筆、整個蓋回去」，中間完全沒有防護，於是：如果你同時開好幾個視窗設定
好幾組連線，會憑空少掉好幾組（我這次測到八個一起設定，改之前平均只留一到
三組，改之後八個全部都在）；如果寫到一半當機或磁碟滿了，整個檔案可能被
截斷成一堆半吊子文字，連同其他不相干的設定一起壞掉；刪除一組設定時，
如果你的系統鑰匙圈剛好鎖住，密碼可能留在鑰匙圈裡卻沒有任何畫面看得到它、
刪得掉它。**改之後**，這三個坑都補上了：多組同時寫入會排隊、不會互相蓋掉；
寫到一半失敗，檔案會維持改之前的樣子，一個字元都不會少；刪除時鑰匙圈失敗
會清楚地告訴你「刪除失敗，去解鎖鑰匙圈再試一次」，而不是悄悄裝作已經刪掉。

### 3. 刪除一組設定時，要先刪鑰匙圈裡的密碼再刪欄位；鑰匙圈刪不掉時要老實回報失敗

**這一條是重驗過的，版本 `a1eae69`。原本第一次驗證用錯了失敗情境，說明見下。**

- **第一次驗證錯在哪裡**：我第一次測「鑰匙圈刪不掉」這個情境時，讓假鑰匙圈
  丟出「鑰匙圈被鎖住」這個錯誤型別。這確實是系統文件上「被鎖住」該丟的
  型別，**但只限於「讀取」密碼的那個函式**。一位審查者實際去讀你電腦上
  真正安裝的鑰匙圈程式庫原始碼，發現「刪除」密碼的那個函式寫法不一樣：
  不管是密碼不存在、還是鑰匙圈被鎖住、還是任何其他系統錯誤，一律丟出
  **另一個型別**（`PasswordDeleteError`）。也就是說，我第一次驗證時測的
  那個情境（刪除時丟出「被鎖住」型別），**在你真正的電腦上永遠不會發生**；
  我等於是測了一個假想的失敗，剛好又是舊程式本來就會正確處理的那一種
  （舊程式把這個型別當成「密碼本來就不存在」），所以第一次驗證看起來
  通過，但那個通過沒有意義——它沒有測到真正的問題。真正的問題是：舊程式
  把「刪除失敗（因為被鎖住）」跟「密碼本來就不存在」搞混，因為這兩種
  情況在「刪除」這個函式上，系統丟出來的是**同一個**錯誤型別。

- **我這次怎麼試的**：把假鑰匙圈的「刪除」動作改成丟出真正會發生的那個
  型別（`PasswordDeleteError`），而且是在**密碼確實存在**的情況下丟出來
  （模擬「密碼在，但鑰匙圈當下鎖住刪不掉」）。另外補了兩個情境：密碼
  **本來就不存在**時（呼叫「讀取」而不是「刪除」去確認，讀到的結果是
  「沒有」），刪除要能安靜地成功，而且**不能去呼叫「刪除」那個函式**
  ——因為對一個本來就不存在的密碼呼叫刪除，一樣會丟出同一個型別，程式
  沒辦法只憑這個型別分辨「不存在」跟「刪不掉」，所以必須先用另一個方式
  確認密碼在不在。第三個情境是正常的刪除成功。

- **結果**：

  1. **密碼存在、刪除被鑰匙圈拒絕**：刪除呼叫**丟出了需求書指定的那個
     專屬錯誤型別**，而且附帶著真正的系統錯誤原因；設定欄位**完全沒被
     動過**，鑰匙圈裡的密碼也**還在原地**——你解鎖鑰匙圈之後可以再刪一次。
  2. **密碼本來就不存在**：刪除**安靜地成功**（回報「有這組設定，刪掉了」），
     而且程式**確實沒有去呼叫「刪除」那個函式**——避免了「不存在」跟
     「刪不掉」被同一個錯誤型別混在一起的陷阱。
  3. **正常刪除**：密碼與設定欄位**兩邊都乾淨地消失了**。

- **證據**：情境 1 的例外型別名稱與附帶原因、失敗當下讀出的欄位內容
  （仍然完整）、鑰匙圈裡的密碼（仍在）；情境 2 「刪除」函式是否被呼叫過
  的紀錄（沒有）與最終欄位狀態（已清空）；情境 3 刪除前後兩邊的狀態
  （都已清空）。三個情境跑在這個分支目前的版本（`a1eae69`）上，全部
  符合預期。

- **順手多驗的一項（需求方要求，成本低就做）**：這次改動同時也讓「寫入
  成功之後、把檔案權限改回去」這一步的失敗不再被誤判成整個寫入失敗。
  我讓「改權限」這一步直接丟出系統錯誤，確認：寫入呼叫**沒有**跟著丟出
  錯誤、而且新內容**確實**已經寫進檔案裡——一次成功的寫入不會因為權限
  這種次要的收尾動作失敗，就被使用者看成「寫入失敗」而重試，重試才是
  真正可能造成重複寫入或衝突的動作。

- **誠實說明**：「先刪密碼」這個順序本身，是這次修改**新加上去**的；
  「鑰匙圈失敗時欄位不受影響」這件事，以及專屬錯誤型別的存在，也是這次
  一起做的。如果只看「刪除最終能不能成功」，改之前在「密碼本來就不存在」
  這條路上也能刪成功——這次真正補上的是「密碼存在、但刪不掉時，讓你知道
  刪不掉了，而不是悄悄把它當成不存在，留一顆孤兒密碼在鑰匙圈裡」。

- **判定：PASS（通過）——這是重驗後的結論，取代第一次驗證的結果，不是
  對同一個結論疊加一次確認。**

- **證據**：兩個情境刪除前後讀出的指標值（情境一：`X` → 空；情境二：
  `Y` → `Y`，不變）。

- **判定：PASS（通過）**

### 5. 需求書隨附的併發測試，在改動前的舊程式上要是紅的，在這次的版本上要是綠的

- **我怎麼試的**：這條是最容易被「其實沒換到程式」這個陷阱騙過去的一條，

### 6. 一次寫入或刪除，除了正在動的那一組之外，之前就存在的其他設定要一字不動地留著

## 除了七條驗收條件之外，我還試著把資料弄丟

### 設定檔如果是一個連到別處的捷徑（symlink）呢？

需求書提到之前有一版曾經把這種捷徑「寫壞」——寫入時捷徑消失、變成一個
普通檔案，真正的目標檔案從此再也收不到新設定。我實測：把設定檔位置換成
一個指向暫存資料夾外某處的捷徑，寫入一組設定後，**捷徑本身還在、還是
指向原本的目標**，而且新設定**確實出現在捷徑指向的那個真正檔案裡**。
沒有被寫壞。

### 寫到一半被強制關閉（比磁碟故障更粗暴）呢？

我用真正的系統訊號，在寫入行程「已經開了暫存檔、還沒改名成正式檔案」的
那個瞬間直接強制終止它，重複三次。結果：

- **確實會留下垃圾**：三次強制關閉，設定資料夾裡確實累積了三個沒人清掉的
  暫存檔案（這是任何「先寫暫存檔再改名」的設計在被強制關閉時都躲不掉的
  物理限制）。
- **下一次正常寫入會自動清掉**：我把這些垃圾檔案的時間戳改成看起來已經放了
  一天，再讓程式做一次正常寫入，垃圾**確實被清乾淨**。
- **清理不會誤殺正在寫的人**：我模擬一個「正在寫入、還沒寫完」的行程，
  它自己留下的暫存檔案是全新的（不到一天），清理動作在同一時間跑，
  **完全沒有動到這個還活著的暫存檔**。
- **清理不會動到你自己的備份**：我在資料夾裡放了一個你可能自己建立的
  `config.toml.backup` 檔案，清理前後內容**一字不動**。

### 用奇怪的設定名稱去踩邊界呢？

我試了空字串、名字裡帶換行、名字是 `../something`、名字裡帶 NUL 位元組、
一個 4096 字元的超長名字。五種**全部寫入成功、讀得回來、沒有讓程式當掉**，
也**沒有任何一種讓寫入的位置跑到設定資料夾以外**——因為這個名字只是存進
設定檔內部的一個欄位名稱，從來不會被當成檔案路徑的一部分去組合，所以
`../something` 這種路徑穿越手法在這裡沒有機會發揮作用。這點我認為是
這個設計本來就穩妥的地方，不是這次修改新補的洞。

## 跑對抗測試時的意外發現

在重新跑那六支對抗測試程式時，其中一個測試案例失敗了，原因跟這次改的
程式碼**完全無關**：這個測試案例本身**沒有把系統鑰匙圈換成假的**，
所以它實際去呼叫了你電腦上**真正的系統鑰匙圈**，想在裡面寫入一筆測試用
的假密碼（服務名稱 `redshift-comment-mcp`、帳號 `prod`、密碼就是英文
單字 `pw`）。這次呼叫在我的環境裡失敗了，所以**這次沒有寫入新東西**。

但我進一步查證後發現：你的系統鑰匙圈裡，**已經有一筆一模一樣的紀錄**，
建立時間是「這次驗證開始之前」（不是我這次的驗證造成的），密碼同樣是
`pw`——這代表**在更早的某一次驗證這個專案的過程中，同一個測試案例的
這個問題已經真的把一筆測試假密碼寫進你的系統鑰匙圈裡了**，而且從建立
到現在都沒有再被改過，所以那不是這次驗證留下的，是更早就在的。我只有
「查詢」這筆紀錄是否存在（確認它是不是被我這次寫入的），**沒有修改、
沒有刪除它**。

這件事跟這次要驗收的「設定檔存 profile」完全無關，也不是這次修改
（`a1eae69`）造成的——問題出在專案自己一支**既有的**測試程式忘記把
鑰匙圈換成假的。但因為它牽涉到你電腦上真正的系統鑰匙圈，我認為值得
明確告訴你，而不是輕輕帶過。要不要清掉那筆遺留下來的測試假密碼、要不要
順手把那支測試程式也修好，我列在下面「我不確定你要不要」那一節，交給
