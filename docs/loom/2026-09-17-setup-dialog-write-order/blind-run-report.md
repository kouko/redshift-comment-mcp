# 設定精靈不再留下半套設定 — 我實際試了什麼、結果如何

**結論：四條驗收條件全部通過（PASS）。原本的攻擊路徑已經關閉。**

試用日期：2026-09-17。在專案的一份全新乾淨副本（版本 `367a05d`）上進行，
沒有動到你電腦上真正的設定檔，也沒有動到你真正的鑰匙圈（Keychain）。

---

## 這個修改對你來說是什麼意思

你在對話中請 AI 幫你設定 Redshift 連線時，它會跳出一個系統密碼視窗。

**改之前**：AI 會先把你給的主機位址、帳號、資料庫名稱寫進設定檔，**然後才**
跳密碼視窗。只要這一步失敗——你按了取消、macOS 擋下視窗、系統沒有對話框工具、
平台不支援、或你按了確定但沒打字——設定檔就已經被改成新主機了，而鑰匙圈裡
還留著**舊的、仍然有效的**密碼。

後果：你的設定檔指向一個新主機，配上你原本那組真的密碼。下一次任何一個
資料庫動作，都會拿你的真密碼去登入那個新主機。而系統還會回報「已設定完成」。

**改之後**：密碼先拿到手，才動任何一個儲存位置。拿不到密碼就什麼都不寫。
連「密碼拿到了、但鑰匙圈拒絕寫入」這種中途失敗，也會把設定檔**原封不動地
還原**，連檔案權限都還原。

## 你要求的四件事，一條一條試

### 1. 密碼那一步因為五種原因中的任何一種失敗之後，設定檔的內容與呼叫之前一字不差

- **我怎麼試的**：我先做出一個「已經在正常使用」的狀態——設定檔裡有一個叫
  `default` 的設定，指向 `old-host.example.com`、帳號 `alice`、資料庫
  `analytics`；鑰匙圈裡放著 `OLD-PASSWORD`。然後我用一個假的密碼視窗，
  分別讓它以五種方式失敗（按取消／權限被擋／找不到對話框工具／平台不支援／
  按確定但沒打字），每次都用「攻擊者主機 `attacker-host.example.com`、
  帳號 `mallory`、資料庫 `prod`」去呼叫設定精靈。每一次我都在呼叫前後把
  設定檔的原始位元組和檔案權限完整讀出來比對。

- **結果**：五種失敗全部一樣——

  ```
  呼叫前 (權限 600): b'[profile.default]\nhost = "old-host.example.com"\n
                      port = 5439\nuser = "alice"\ndbname = "analytics"\n'
  呼叫後 (權限 600): b'[profile.default]\nhost = "old-host.example.com"\n
                      port = 5439\nuser = "alice"\ndbname = "analytics"\n'
  位元組完全相同: True    檔案權限完全相同: True
  ```

  我另外還試了一份「人手寫過、排版很亂」的設定檔（含註解、Windows 換行、
  日文值、亂序的欄位、一個程式不認識的額外欄位、兩組設定），因為只是「重新
  存一次」的話，這種檔案一定會被格式化、比對就會露餡。結果也是一字不差。

  我還試了一台**完全沒有設定檔**的新電腦：按取消之後，設定檔沒有被建立出來。

- **證據**：五種失敗情境的前後位元組完整輸出（如上）；專案隨附的對抗測試中
  `probe_config_toml_byte_identity` 的兩個案例、共 6 個組合全部通過。

- **判定：PASS（通過）**

### 2. 這種失敗之後，該設定在鑰匙圈裡的那筆密碼沒有被動過

- **我怎麼試的**：同上五種失敗情境，每次都把假鑰匙圈的完整內容在呼叫前後
  印出來比對。

- **結果**：五種失敗全部一樣——

  ```
  呼叫前: {('redshift-comment-mcp', 'default'): 'OLD-PASSWORD'}
  呼叫後: {('redshift-comment-mcp', 'default'): 'OLD-PASSWORD'}
  完全相同: True
  ```

  補充一點誠實的說明：這一條在**改之前就已經成立**——舊程式在這五條路上
  同樣碰不到寫密碼那一步。所以這一條是「確認沒有被改壞」，不是「修好了」。
  真正壞掉的是第 1 條。

  額外收穫：我另外測了「密碼拿到了，但鑰匙圈當下被鎖住拒絕寫入」。這在
  真實世界是很常見的狀態。結果設定檔被完整還原、鑰匙圈維持舊密碼、回覆訊息
  明確告訴使用者「兩邊都沒動」。

- **證據**：五種失敗情境的鑰匙圈前後內容（如上）；額外的鑰匙圈拒絕寫入情境，
  回覆為 `keychain_write_failed`、訊息中明寫「rolled back … both stores are
  untouched」，且設定檔位元組相同。

- **判定：PASS（通過）**

## 額外：我直接重演了原本的攻擊

情境：你已經有一組能用的設定與密碼，AI 用一個**不同的主機位址**呼叫設定精靈，

| | 設定檔裡的主機 | 鑰匙圈裡的密碼 | 設定檔一字不差？ |

## 我不確定你要不要

1. **那兩個失敗的測試要不要在這個 PR 一起處理？** 它們是既有問題，但它們的
   存在意味著「需要真實資料庫的那一層測試現在不是全綠的」。如果你的習慣是
   「合併前那一層必須全綠」，這就得先解決；如果你把它當成獨立的技術債，
   這次就可以照原樣出。

2. **專案文件上的測試指令在全新下載的副本上跑不起來，要不要一併修？**
   我在一份全新副本上第一個動作就是照文件跑測試，結果是六個測試檔全部
   無法載入。原因是測試工具被歸在「選用套件」裡，執行工具不會自動裝它，
   於是它去用了你電腦上剛好存在的另一套 Python，那套 Python 裡沒有這個
   專案。要先手動多跑一個安裝指令才會正常。這會讓任何第一次接手這個專案
   的人（或 CI）第一步就卡住。同樣是既有問題。

3. **要不要把那個空的設定資料夾也一起清掉？**（見上一節第一點）

4. **有一個新加的測試，在它失敗的時候會真的去對外查 DNS。** 正常情況下
   （修改正確時）它不會走到那一步，我實測新版跑完只花 0.97 秒、沒有連外。
   但在舊程式上跑它時，它確實對 `new.example.com` 發出了真實的名稱查詢。
   如果你希望「不需要資料庫的那層測試」永遠不碰網路，這裡值得補一個擋板。
